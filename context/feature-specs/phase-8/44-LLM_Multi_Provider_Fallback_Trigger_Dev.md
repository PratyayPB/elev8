# LLM Multi-Provider Fallback Architecture with Trigger.dev

## Objective

Implement a reliable multi-provider fallback layer for **all LLM API calls made by the application**, primarily to reduce development-time failures caused by exhausted free-tier quotas/rate limits.

Current providers:

1. Google AI Studio / Gemini API
2. Groq API
3. OpenRouter API

The implementation must use **Trigger.dev Jobs/Tasks** for the LLM workflows that are already suitable for asynchronous/background execution, while keeping the provider abstraction reusable from every part of the application.

> Important: Trigger.dev retries and provider fallback solve different problems. Trigger.dev provides durable execution/retries; the provider router decides when to switch from Gemini → Groq → OpenRouter.

---

Before changing code, inspect the repository and identify:

- Every current Gemini API call
- Every current Groq API call
- Existing AI/LLM utility files
- Existing Trigger.dev tasks/jobs
- Existing `trigger.config.*`
- Existing API routes/server actions that invoke LLMs
- Existing streaming responses
- Existing structured JSON/schema output
- Existing tool/function calling
- Existing model names
- Existing environment variables
- Existing error-handling/retry logic
- Existing logging/observability
- Existing database persistence for generated AI results

Create a short internal map of:

```text
LLM Call
  ↓
Current caller
  ↓
Current provider
  ↓
Expected output format
  ↓
Synchronous or background workflow
```

Do not blindly replace existing implementations.

# 2. Target Architecture

Create a single provider-independent LLM service:

```text
Application
   │
   ▼
LLM Service / Router
   │
   ├── Gemini Adapter
   │
   ├── Groq Adapter
   │
   └── OpenRouter Adapter
```

For asynchronous workflows:

```text
Application
   │
   ▼
Trigger.dev Task
   │
   ▼
LLM Router
   │
   ├── Gemini
   │     └── failure/quota/rate-limit
   │
   ├── Groq
   │     └── failure/quota/rate-limit
   │
   └── OpenRouter
          └── failure
                ↓
             Final failure
```

The application should not contain provider-specific fallback logic such as:

```ts
tryGemini()
catch {
  tryGroq()
}
```

inside individual features.

Instead:

```ts
await llm.generate(...)
```

or the project's equivalent abstraction should handle provider selection centrally.

# 3. Provider Interface

Create a common internal interface.

Conceptually:

```ts
interface LLMProvider {
  name: "gemini" | "groq" | "openrouter";

  generate(request: LLMRequest): Promise<LLMResponse>;
}
```

The exact types should be adapted to the existing application.

The normalized request should support the features the application actually uses, potentially including:

- system instructions
- user messages
- model
- temperature
- max output tokens
- structured JSON output
- JSON schema
- tool/function calling
- multimodal content if currently used
- streaming if currently used

Do not add unsupported abstractions merely for theoretical completeness.

---

# 4. Provider Fallback Policy

Default development fallback order:

```text
1. Gemini
2. Groq
3. OpenRouter
```

Make this configurable through environment variables/configuration rather than hardcoding it throughout the codebase.

Example:

```env
LLM_FALLBACK_ORDER=gemini,groq,openrouter
```

Allow the primary provider/model to be configured independently.

Example:

```env
LLM_PRIMARY_PROVIDER=gemini

GEMINI_MODEL=...
GROQ_MODEL=...
OPENROUTER_MODEL=...
```

Do not commit API keys.

---

# 5. What Counts as a Fallback-Eligible Error?

Fallback should generally happen for transient/provider-capacity failures such as:

- HTTP 429 / rate limit
- quota exhaustion
- provider overload
- temporary unavailable errors
- HTTP 5xx provider errors
- network timeout
- connection failure
- provider-specific temporary availability errors

Fallback should **not automatically happen** for errors indicating that changing providers will not fix the request, such as:

- malformed application request
- invalid internal parameters
- invalid schema generated by the application
- authentication/configuration errors caused by missing API keys
- programming errors
- unsupported feature that every provider implementation would fail on

However, provider authentication failures should be logged clearly and the router may continue to another configured provider if the failure is isolated to that provider.

Define an explicit classifier:

```ts
classifyLLMError(error): {
  fallbackEligible: boolean;
  reason: string;
}
```

Do not rely solely on string matching.

---

# 6. Do NOT Confuse Trigger.dev Retry with Provider Fallback

Trigger.dev retry:

```text
Same task
   ↓
same provider/request
   ↓
retry
```

Provider fallback:

```text
Gemini
   ↓ failure
Groq
   ↓ failure
OpenRouter
```

Use both where appropriate.

Recommended strategy:

```text
Trigger.dev Task
   │
   ├── LLM Router
   │      ├── Gemini
   │      ├── Groq
   │      └── OpenRouter
   │
   └── Task-level retry for failures that remain retryable
```

Avoid multiplying requests unnecessarily.

For example, do not blindly configure:

```text
3 Trigger retries × 3 providers
```

if that can result in 9 expensive/duplicate LLM calls.

Define the retry/fallback behavior deliberately.

Trigger.dev supports task retries, conditional error handling, and retry helpers, so use its native mechanisms rather than implementing a competing job system. See the official Trigger.dev documentation/source material: https://trigger.dev/

# 7. OpenRouter Integration

OpenRouter provides an OpenAI-compatible API.

Official endpoint:

```text
https://openrouter.ai/api/v1/chat/completions
```

Authentication:

```http
Authorization: Bearer <OPENROUTER_API_KEY>
```

The request includes a model slug and messages.

Example:

```ts
const response = await fetch(
  "https://openrouter.ai/api/v1/chat/completions",
  {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${process.env.OPENROUTER_API_KEY}`,
    },
    body: JSON.stringify({
      model: process.env.OPENROUTER_MODEL,
      messages,
    }),
  }
);
```

OpenRouter is also compatible with the OpenAI SDK by changing the base URL:

```ts
const client = new OpenAI({
  baseURL: "https://openrouter.ai/api/v1",
  apiKey: process.env.OPENROUTER_API_KEY,
});
```

Official OpenRouter Quickstart:

https://openrouter.ai/docs/quickstart

OpenRouter documentation states that the OpenAI-compatible API supports `/api/v1/chat/completions` and model slugs from its model catalog.

Do not assume that a Gemini model name or Groq model name can be sent to OpenRouter unchanged.

Use:

```env
OPENROUTER_MODEL=provider/model-name
```

with a valid OpenRouter model slug.

The model must be selected/configured based on the application's requirements.

# 8. OpenRouter Free Models

Because this project is specifically intended to reduce development-time free-tier exhaustion:

- Prefer a configured OpenRouter model rather than hardcoding one.
- Verify that the selected model is currently available before implementation.
- Do not assume a model will remain free forever.
- Keep the model configurable through environment variables.
- Document the currently selected model in `.env.example`.
- If OpenRouter's model catalog changes, the application should not require a code change merely to change the fallback model.

OpenRouter also supports model-level fallback routing internally. However, this project primarily requires **cross-provider fallback**, because Gemini and Groq use separate API credentials.

Do not replace the three-provider architecture with OpenRouter-only fallback.

# 10. Trigger.dev Task Design

Use Trigger.dev for workflows that are naturally asynchronous, long-running, retryable, or already implemented as background jobs.

Examples in this application may include:

- interview generation
- roadmap generation
- career assessment
- resume analysis
- resume scoring
- large AI generation workflows
- batch AI processing

A conceptual task:

```ts
export const generateSomething = task({
  id: "generate-something",

  run: async (payload) => {
    const result = await llm.generate({
      ...payload,
    });

    return result;
  },
});
```

The task should not know whether Gemini, Groq, or OpenRouter ultimately produced the response.

It should only know about the normalized LLM service.

# 11. Preserve Existing Output Contracts

This is critical.

If an existing feature expects:

```json
{
  "questions": [],
  "metadata": {}
}
```

then switching providers must not change the application's contract.

The router should normalize provider responses into a common structure.

For example:

```ts
interface LLMResponse<T = unknown> {
  content: string;
  parsed?: T;

  provider: "gemini" | "groq" | "openrouter";
  model: string;

  usage?: {
    inputTokens?: number;
    outputTokens?: number;
    totalTokens?: number;
  };
}
```

Adapt this to the application's current architecture.

Do not unnecessarily expose provider-specific response objects throughout the application.

---

# 12. Structured Output

If existing LLM calls use JSON/schema output:

1. Preserve the existing schema.
2. Make the provider adapters translate the schema into the provider's supported format.
3. Validate the final response.
4. If parsing/validation fails, determine whether retrying another provider makes sense.
5. Never silently accept malformed JSON.

Preferred flow:

```text
LLM
 ↓
Raw response
 ↓
Parse
 ↓
Schema validation
 ↓
Valid?
 ├── Yes → return
 └── No → provider failure classification / retry strategy
```

Use the application's existing validation library if one already exists, such as Zod.

# 15. Important: Avoid Duplicate Generation

The fallback system must not accidentally create duplicate resources.

For example:

```text
Trigger task starts
      ↓
Gemini succeeds
      ↓
Database write succeeds
      ↓
Task crashes before completion acknowledgement
      ↓
Trigger retries
      ↓
LLM gets called again
```

This can produce duplicate AI generations.

Where the existing workflow creates persistent resources:

- use an idempotency key
- check whether the requested generation already completed
- persist status transitions carefully
- make database writes idempotent

Prefer:

```text
PENDING
  ↓
GENERATING
  ↓
COMPLETED
```

with safe retry behavior.

---

# 16. Timeout Policy

Every provider call should have a timeout.

Do not allow an unavailable provider to block the entire Trigger task indefinitely.

Conceptually:

```text
Gemini
  ↓
timeout
  ↓
Groq
  ↓
timeout
  ↓
OpenRouter
```

Use reasonable provider-specific timeouts based on the application's existing workload.

Do not choose extremely aggressive timeouts for long generation tasks.

---

# 17. Do Not Automatically Fallback for User-Cancelled Jobs

If the user cancels a Trigger.dev run or the application intentionally aborts the operation:

```text
cancel
 ↓
stop
```

Do not interpret cancellation as provider failure and invoke additional providers.

# 18. Streaming

First inspect the codebase.

If the application currently uses streaming LLM responses:

- do not blindly move streaming calls into Trigger.dev
- do not break the existing user-facing streaming UX
- design a separate streaming-capable provider abstraction if required

Trigger.dev is primarily useful for durable background workflows. A request that requires immediate token streaming to a browser may need to remain in an API/server action path.

The multi-provider abstraction should still be reusable.

# 22. Quality / Capability Matching

Fallback should not blindly select a provider that cannot perform the required operation.

For example, if a feature requires:

- structured output
- tool calling
- vision
- very large context
- a particular reasoning capability

the router should verify that the fallback model supports the required capability.

A fallback provider should be:

```text
available
+
compatible
+
configured
```

Otherwise skip it.

# 23. Fallback Algorithm

Conceptually:

```ts
for (const provider of fallbackOrder) {
  if (!isConfigured(provider)) {
    continue;
  }

  if (!supportsRequest(provider, request)) {
    continue;
  }

  try {
    return await provider.generate(request);
  } catch (error) {
    const classification = classifyLLMError(error);

    logFailure(provider, classification);

    if (!classification.fallbackEligible) {
      throw error;
    }
  }
}

throw new AllProvidersFailedError(...);
```

Do not swallow the original errors.

The final error should retain enough context to diagnose:

```text
all configured providers failed
```

while avoiding secret leakage.

---

# 24. Trigger.dev Retry Configuration

Inspect the project's existing Trigger.dev version and conventions before implementing.

Use native Trigger.dev retry configuration where appropriate.

Do not introduce retry loops inside every provider adapter.

A sensible separation is:

```text
Provider adapter
→ one provider request

LLM router
→ switch providers

Trigger task
→ durable task retry / recovery
```

This keeps responsibilities clean.

# 29. Important Architectural Decision

Do **not** rewrite the entire AI layer just because three providers are being introduced.

Prefer an incremental refactor:

```text
Existing Gemini call
       ↓
Gemini adapter
       ↓
LLM router
       ↓
Gemini → Groq → OpenRouter
```

Then migrate other LLM calls one feature at a time.

After each migration:

1. run tests
2. run TypeScript checks
3. run lint
4. manually test the feature
5. verify Trigger.dev execution
6. verify fallback behavior

# 31. Final Implementation Principle

The goal is **not** to create a complicated AI infrastructure platform.

The goal is:

```text
                 ┌── Gemini
                 │
Application → LLM Router ── Groq
                 │
                 └── OpenRouter
                         │
                         ▼
                    Normalized result
                         │
                         ▼
                    Application
```

The rest of the application should remain unaware of which provider answered the request.

The provider layer should be replaceable.

If Gemini's free quota is exhausted:

```text
Gemini ❌
   ↓
Groq ✅
```

If both are unavailable:

```text
Gemini ❌
   ↓
Groq ❌
   ↓
OpenRouter ✅
```

If all providers fail:

```text
Gemini ❌
Groq ❌
OpenRouter ❌
   ↓
Controlled failure
```

This architecture should provide resilience during development without unnecessarily turning the application into a complex distributed AI infrastructure system.
